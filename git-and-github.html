Team handbook

Ship work every day with Git and GitHub.

You do not need to memorize Git. Learn one picture, then follow the same 8 steps on every ticket. This page is written for everyone on the team — not only specialists.

Git

Your notebook

A tool on your computer. It saves snapshots of your files so you can try ideas, go back, and combine work without losing anything.

GitHub

The shared filing cabinet

A website where the team stores the project, reviews each other’s work, and keeps main safe before anything is released.

1Git vs GitHub

If you remember only one sentence: Git records history on your machine. GitHub is where the team shares and reviews that history.

ThingWhereWhat it means for you
Files you editYour computerThis is your working copy. Nobody else sees it yet.
CommitGit, on your computerA saved snapshot with a short message.
PushTo GitHubNow the team can see your branch.
Pull requestGitHub“Please review this and put it on main.”
You can use Git without GitHub. A team cannot use GitHub well without Git.

2The big picture

Almost every command moves work between these four places. When you feel lost, ask: “Which box am I in?”

1. Working filesWhat you edit in Visual Studio or Cursor. Unsaved Git history.
2. StagingA shopping cart. You choose which changes go into the next snapshot.
3. Local GitCommits saved in the hidden .git folder. Safe even if the internet is down.
4. GitHubThe shared copy. Other people only see work after you push.
edit files →
git add →
git commit →
git push

A branch is not a full copy of the project. It is a label that says “this line of work ends here.” Creating a branch is cheap. Use a new one for every ticket.

3One-time setup

Do this once on a new machine. Then you can ignore this section.

Tell Git who you are

git config --global user.name "Your Name"
git config --global user.email "you@company.com"

Use the same email as GitHub.

Get the project

git clone git@github.com:org/repo.git
cd repo

That folder is your local copy. GitHub is still the shared original.

On Windows, Git often comes with Visual Studio. Check with git --version. Sign in to GitHub with SSH or GitHub CLI (gh auth login) so you never type a password into Git.

4Your daily workflow

This is the whole job. Repeat it for every ticket. Tick the boxes as you learn the habit — they stay saved in this browser.

Update main

Never start work on yesterday’s code.

git checkout main
git pull

Create a branch

One ticket, one branch. Do not commit on main.

git checkout -b feature/short-ticket-name

See what changed

When you feel lost, this is the first command.

git status
git diff

Save a snapshot

Stage only the files that belong in this idea. Then commit.

git add path/to/file
git commit -m "Add CSV export for the user list"

Share the branch

The first push needs -u so Git remembers GitHub.

git push -u origin HEAD

Open a pull request

On GitHub, compare your branch to main. Write why the change exists. Ask for review. Or:

gh pr create --fill --base main

Update the same PR

Review comments are not a new ticket. Commit on the same branch and push again. The PR updates by itself.

git add path/to/file
git commit -m "Address review: handle empty export"
git push

Clean up after merge

Come home to a fresh main.

git checkout main
git pull
git branch -d feature/short-ticket-name

5Branches, in plain language

Think of main as the hallway everyone walks through. Your branch is a side room. You decorate the room, then ask the team to accept it back into the hallway.

Good names

feature/user-export-csv
fix/login-timeout
chore/upgrade-packages

Habits that help

Keep branches short-lived. Do not mix two tickets on one branch. Merge main into your branch if the work lasts more than a day.

git fetch origin
git merge origin/main

6Commits people can read

Write the message like a command: what this snapshot does.

Fix timeout when the login service is slow

fixed stuff / wip / asdf / updates

Never commit passwords, connection strings, or personal settings. If a secret gets in, rotate it. Deleting the file later is not enough — history still has it.

Look at files before you stage everything. git add . is fast and also how junk gets in.

7Pull requests — how the team ships

A pull request is not a Git object. Git only knows commits and branches. GitHub adds the conversation, checks, and merge button.

Do thisWhy
Keep the PR smallPeople actually review it.
Explain why, not only whatReviewers cannot see the ticket in your head.
Wait for checksA red build means “not ready.”
Use Draft until it is readyStops accidental merge and noisy review.

GitHub can merge by creating a merge commit, squashing into one commit, or rebasing. Use the repo default. Do not fight it on every PR.

Merge vs rebase, short version: merge keeps the true history and is safer on shared branches. rebase replays your commits on top of latest main and rewrites hashes. Never rebase main. Never force-push main.

8Conflicts are normal

A conflict only means two people edited the same place. Git is asking you to choose the final text.

  1. Open the marked file. You will see <<<<<<<, =======, and >>>>>>>.
  2. Edit it into the correct finished code. Delete the markers.
  3. Stage the file: git add path/to/file
  4. If you were merging: git commit. If you were rebasing: git rebase --continue.

Need to bail out? git merge --abort or git rebase --abort returns you to before you started.

9Undo, without panic

Run git status first. Most “undo” commands move a pointer. A few throw away uncommitted work — those are marked.

I want to…Command
Unstage a file, keep the editsgit restore --staged file
Throw away uncommitted edits in a filegit restore file (destructive)
Fix the last commit message (not pushed)git commit --amend -m "Better message"
Undo last local commit, keep filesgit reset HEAD~1
Undo a commit already on maingit revert HASH then push
Park unfinished work and switch branchgit stash push -m "wip" then later git stash pop
If the bad commit is already on shared main, do not rewrite history. Use git revert. That adds a new commit that undoes the old one.

10Common problems

Git will not let me switch branches

You have unsaved changes Git would overwrite. Commit them, stash them, or discard them.

git stash push -m "wip"
git switch other-branch
I committed on main by mistake (not pushed) 
git branch feature/move-this
git reset --hard origin/main
git switch feature/move-this
git push -u origin HEAD
Push was rejected — remote has work I do not have

Pull first, then push. Do not force-push unless it is your private branch and you understand the risk.

git pull
git push
I need yesterday’s file, but I want to keep current history 
git checkout main -- path/to/file
git commit -m "Restore file from main"
Permission denied (publickey)

Your SSH key is not loaded or not added in GitHub → Settings → SSH keys. Test with ssh -T git@github.com.

11Cheat sheet

Keep this nearby. After a few weeks you will not need it.

Where am I?
git status · git log --oneline -10
Start a ticket
git switch main · git pull · git switch -c feature/name
Save work
git add -p · git commit -m "Why this changed"
Share it
git push -u origin HEAD
Refresh from main
git fetch origin · git merge origin/main
Finish
git switch main · git pull · git branch -d feature/name

12Thirty-minute practice

Do this once on a throwaway GitHub repo. After it feels boring, you know enough for daily work.

  1. Clone the repo, create a branch, add a file, commit, push, open a PR, merge it.
  2. Make two branches that edit the same line. Merge both and resolve the conflict.
  3. Amend a commit you have not pushed.
  4. Revert a commit you have pushed.
  5. Stash work, switch branches, then pop the stash.
Team rules belong at the top of this page if you have them: branch prefixes, squash-only merges, required reviewers. Write them down so nobody has to guess.
